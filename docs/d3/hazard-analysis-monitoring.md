The analysis is bottom-up: it starts from the five safety-critical functions identified in D2 (safety-critical specifications, section 1) and, for each module that realizes them, asks how it can fail and where the failure leads. A *failure mode* is what goes observably wrong; its *causal factors* are the faults, in the code or in the environment, that can produce it. Rows are ordered by function, not by a risk score: as seen in the course, a single Occurrence × Severity × Detection number can rank a nuisance as high as a patient-harm hazard, so every row below is kept because its system effect can hurt a patient or hide who is accountable.

## 2.3 FMEA table - Monitoring System

| ID | Component | Failure mode | Causal factors | Immediate effect | System effect (hazard / harm) |
| --- | --- | --- | --- | --- | --- |
| F-MON-01 | Cabinet Health Monitor (`checkTimeouts`) | A cabinet that stopped sending heartbeats stays displayed ONLINE, or goes OFFLINE without a communication loss alarm | Scheduler stopped or blocked; storage failure while the status change or the alarm is written; server clock not synchronized with the hospital time server | Connectivity not updated; no communication loss alarm | Nobody goes to check a dead cabinet; a nurse relies on it and cannot get the medication: **delayed treatment** |
| F-MON-02 | ADC Communication Manager (`receiveHeartbeat`) and Alarm Manager (`recordFromAdc`) | An alarm sent by an ADC is acknowledged "received" but never stored | Acknowledgement sent before the storage completes; storage failure after the answer; an alarm rejected by a validation that is too strict | The ADC deletes the alarm from its memory; the Monitoring System has no trace of it | A temperature excursion or a cabinet fault goes unnoticed; spoiled medication can be **administered to a patient** |
| F-MON-03 | ADC Communication Manager and Historical Data Store (recording of transactions) | A dispensing activity or an alarm sent again by an ADC is recorded twice | The ADC resends a transaction whose acknowledgement was lost on the network, or after an outage; duplicate detection based on the content instead of the transaction identifier; the check and the write not done in one database transaction | Two records for one event in the history; the same alarm shown twice | Consumption reports overstate the use of a medication such as morphine: a false **diversion suspicion** on a nurse, or a real diversion **hidden** among wrong counts; a duplicate alarm sends two people to the same incident |
| F-MON-04 | Alarm Manager (`acknowledge`) | An alarm leaves the list without anybody handling it, or nobody knows who handled it | Acknowledgement by a role that does not handle incidents; two simultaneous acknowledgements overwriting each other; an acknowledgement rewritten or deleted afterwards | The alarm disappears from every dashboard | The incident is **never handled** while everybody believes it is; after an incident, **no accountability** (who saw it, when) |
| F-MON-05 | ADC Communication Manager (`sendCommand`, `sendConfiguration`) | A command is reported "delivered" although the cabinet did not apply it | Any `200` answer taken as success; an answer acknowledging another command or another cabinet; timeout treated as success; a command sent to an offline cabinet | The technician sees "delivered" | A cabinet believed in **maintenance mode keeps dispensing** during a repair, or keeps a wrong configuration: medication dispensed from a cabinet believed out of service |
| F-MON-06 | Inventory Supervisor and Operator Dashboard (stock display, same-floor sources) | An old stock figure is shown as current, or an unreachable cabinet is proposed as a source of a medication | Stock displayed without the time of the heartbeat it comes from; stale label missing; same-floor search not filtering cabinets by their last contact | Wrong stock figure; wrong cabinet proposed | A nurse is **sent to an empty or offline cabinet**: delayed treatment |

## 2.4 Safety requirements - Monitoring System

Each requirement is written as an invariant plus an observable reaction with a time bound, so that it can be tested (section 3.5). The last column names the module that enforces it and, where D2 already stated it, the invariant of the safety-critical specifications.

| ID | Safety requirement | Mitigates | Enforced by (module + invariant) |
| --- | --- | --- | --- |
| SR-MON-01 | When an ADC has sent no valid heartbeat for 45 s, the Monitoring System shall display it UNREACHABLE; when the silence reaches 75 s, it shall display it OFFLINE and raise exactly one communication loss alarm, stored before the status changes. Each change shall happen within 1 s of the threshold. | F-MON-01 | Cabinet Health Monitor, `checkTimeouts` every second; INV-HLT-1, INV-HLT-2; D-15, D-38 |
| SR-MON-02 | The Monitoring System shall acknowledge a transaction as `received` only in a `200` response sent after every transaction of the heartbeat is stored. If the storage fails, it shall answer `500` and acknowledge no transaction, so that the ADC keeps them and sends them again. A transaction whose identifier is already stored shall be acknowledged `received` without being stored again, so that each transaction is recorded exactly once. | F-MON-02, F-MON-03 | ADC Communication Manager, Alarm Manager, Historical Data Store; INV-COM-1, INV-ALM-1; FR-REQ-01, FR-COM-08; D-07, D-28 |
| SR-MON-03 | An alarm shall leave the list of active alarms only through an acknowledgement by a nurse, pharmacist or technician. The acknowledgement records who and when, is never rewritten, and a second acknowledgement of the same alarm is refused with the name and time of the first one. | F-MON-04 | Alarm Manager (`acknowledge`) and Historical Data Store; INV-ALM-2; NFR-SAF-02, FR-ALM-06; D-09 |
| SR-MON-04 | A command or configuration shall be reported `delivered` only for a `200` answer received within 10 s that repeats its identifier and the identifier of the target ADC; any other answer, or none within 10 s, shall be reported `failed` to the sender. Nothing shall be sent to an ADC displayed OFFLINE, and every sending and its outcome shall be audited. | F-MON-05 | ADC Communication Manager (`deliver`, `readDeliveryAnswer`); INV-CMD-1 to INV-CMD-4; D-04 |
| SR-MON-05 | An ADC silent for 45 s or more shall never be displayed ONLINE; its status and stock shall carry the "stale" label and the time of its last contact, and it shall not be proposed as a same-floor source of a medication. | F-MON-06, F-MON-01 | Cabinet Health Monitor (`getStatus`) and Inventory Supervisor (`findSources`); INV-DSP-1 to INV-DSP-4; NFR-SAF-01, NFR-SAF-03; D-03, D-23 |
