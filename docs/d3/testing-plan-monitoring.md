
# 3. Testing Plan - Monitoring System

This plan tests the Monitoring System independently of the ADC (Part A). Any communication with an ADC is exercised using a fake ADC, stub, or test driver; the plan does not require the two project parts to be integrated.


## 3.4 Test criterion - Monitoring System

Coverage criteria are selected per module based on the complexity of its decisions, its responsibilities, and the potential safety consequences of incorrect behaviour. Branch coverage is targeted for safety-critical decision-making modules, statement coverage for modules primarily responsible for data handling and presentation, and Modified Condition/Decision Coverage (MC/DC) for the compound identifier validation guard in the ADC Communication Manager.

### Coverage Criteria and Justification

| Module | Coverage criterion | Justification |
| --- | --- | --- |
| Cabinet Health Monitor (`CabinetHealthService`) | Branch coverage | Exercises the `ON_SILENCE` connectivity transitions and status decisions in `SPEC-HLT-01` and `SPEC-HLT-02`. Missing a branch could leave an unavailable cabinet appearing operational or prevent a communication-loss alarm from being raised. |
| Alarm Manager (`AlarmService`) | Branch coverage | Exercises alarm recording, duplicate detection, and acknowledgement outcomes. Incorrect decisions could result in lost alarms, duplicate notifications, or modification of an existing acknowledgement. |
| ADC Communication Manager (`AdcCommunicationService` and `protocol.ts`) | Branch coverage and MC/DC | Branch coverage exercises communication outcomes, HTTP errors, and timeouts. MC/DC is applied to the compound identifier check in `readDeliveryAnswer()` because either identifier mismatch must independently prevent a command from being reported as delivered. |
| Inventory Supervisor (`InventoryService`) | Branch coverage | Exercises the low-stock threshold (`< 10`) and stock-source threshold (`> 10`) in `SPEC-INV-01`, including boundary conditions. Incorrect decisions could misrepresent medication availability or recommend an unsuitable cabinet. |
| User Management (`UserService`) | Branch coverage | Exercises role-based permission decisions. Missing a branch could permit unauthorized actions or prevent authorized staff from performing required tasks. |
| Historical Data Store (`HistoryService`) | Statement coverage | Exercises record storage, retrieval, acknowledgement, retention, and report-storage operations. The module primarily handles data persistence and retrieval. |
| Reporting (`ReportingService`) | Statement coverage | Exercises report generation, saving, reopening, filtering, and export operations. The module primarily retrieves, transforms, and presents stored information. |
| Operator Dashboard (`LiveChannel`, presentation helpers, and controllers) | Statement coverage | Exercises status and alarm presentation, payload generation, and controller operations. The module primarily presents information generated by other modules. |
| Clock (`ClockService`) | Statement coverage | Exercises the time-source operation used by other modules. The module supplies time information rather than making safety-critical decisions. |

### MC/DC Test Design

MC/DC is targeted for the compound identifier validation guard in `readDeliveryAnswer()` within the ADC Communication Manager:

`answer.body?.[expected.idField] !== expected.id || answer.body?.adcId !== expected.adcId`

The two conditions are:

- C1: The returned message identifier does not match the expected message identifier.
- C2: The returned ADC identifier does not match the expected ADC identifier.

Each condition must independently affect the decision outcome. Otherwise, the Monitoring System could incorrectly report that a command was successfully delivered.

| Test ID | C1 | C2 | Decision (C1 OR C2) | Expected outcome |
| --- | --- | --- | --- | --- |
| T-MON-10 | False | False | False | Command reported as delivered |
| T-MON-11 | True | False | True | Command reported as failed (`ID_MISMATCH`) |
| T-MON-12 | False | True | True | Command reported as failed (`ID_MISMATCH`) |

Comparing T-MON-10 with T-MON-11 demonstrates the independent effect of C1. Comparing T-MON-10 with T-MON-12 demonstrates the independent effect of C2.

The c8 coverage tool does not directly measure MC/DC. Achievement of this criterion must therefore be demonstrated through the corresponding test cases and their observed results in Section 3.5.

### Coverage Limitations

The module-level coverage percentages include files such as `types.ts`, which contain type definitions and are reported as having zero coverage. Consequently, module-level percentages are lower than those of the corresponding executable service implementations.

Although all 124 tests passed, complete branch coverage was not achieved. Inspection of the reported uncovered lines identifies the following remaining gaps.

| Implementation file | Uncovered behaviour | Explanation and limitation |
| --- | --- | --- |
| `cabinet_health_service.ts` | Storage exception handling (lines 258-260). | The exception propagation and conversion to `StorageUnavailableError` are not fully exercised. The behaviour of the cabinet registry during storage failures therefore remains incompletely verified. |
| `alarms_service.ts` | Unexpected acknowledgement errors and acknowledgement conversion (lines 102 and 168). | The acknowledgement race is tested, but propagation of other exceptions and all outcomes of the acknowledgement conversion expression are not fully exercised. |
| `adc_communication_service.ts` | Internal error response during ADC registration (lines 75-76). | Successful and invalid registration cases are tested, but the internal registration error path remains uncovered. |
| `protocol.ts` | Rejection of an invalid alarm description (lines 110-111). | Invalid transaction handling is tested, but rejection of a description that is neither a string, null, nor undefined remains uncovered. |
| `inventory_service.ts` | Inventory storage exception handling (lines 159-161). | Inventory replacement, stock thresholds, and stock-source selection are tested, but storage exception handling remains incompletely verified. |
| `users_service.ts` | Email fallback for account names and unknown account handling (lines 72 and 128). | Role-based permissions are tested, but all outcomes of account-name resolution and account lookup are not exercised. |

These gaps are primarily associated with defensive error handling, input validation, and exceptional storage conditions. They are retained as testing limitations rather than assumed to be unreachable or irrelevant to system safety.

The reported uncovered lines identify specific coverage gaps but do not necessarily enumerate every uncovered branch within a compound expression.

The existing test suite verifies key safety-related behaviours, including:

- Transition to UNREACHABLE after 45 seconds of silence.
- Transition to OFFLINE after 75 seconds of silence, with exactly one communication-loss alarm.
- Preservation of an existing alarm acknowledgement.
- Prevention of duplicate transaction storage.
- Refusal to send commands to offline ADCs.
- Command delivery failure handling.
- Low-stock threshold and reachable stock-source selection.
- Role-based restrictions on alarm acknowledgement.

MC/DC remains a targeted criterion for the compound identifier validation guard in `readDeliveryAnswer()`. The passing functional tests provide evidence of command failure handling, but the aggregate c8 report does not independently establish that both identifier conditions have been exercised in isolation. Full MC/DC achievement is therefore not claimed.

The measured coverage provides evidence of substantial testing of the Monitoring System's safety-critical behaviour while acknowledging the remaining unverified execution paths.

## 3.6 Integration testing within the Monitoring System

Integrate the Monitoring modules **bottom-up along the USES hierarchy**: test the Clock first, then the Historical Data Store, then the Alarm Manager and User Management, followed by the Cabinet Health Monitor, Inventory Supervisor and Reporting, the ADC Communication Manager, and finally the Operator Dashboard. Use the real lower-level Monitoring modules where available, with a controllable clock and isolated test database; use stubs for lower-level modules that are not part of the test and a fake ADC/test driver to supply valid, invalid, delayed and missing protocol responses at the external ADC boundary. The Dashboard's browser/live-channel output can be driven or observed with test doubles, so no Part A integration is required.
